Learning priorities

  • Keep generated files out of the public repo

    Some tools make temporary files while they work. Those files can be useful for you, but confusing or risky for everyone else if they get published by accident.

    Why it matters: Maintainer tools need safe defaults so launch prep does not pollute public commits.

    Do this next: Run each Creator Kit script once. After each run, check whether it created a new file. If the file is only for local use, ignore it or write it into an output folder.

    Success signal: `git status --short` shows only intentional source changes.

    Triggered by: CY-P2-001

    Learn from: GitHub Docs: Ignoring files

  • Make one place the source of truth

    If the README says one thing, the manifest says another, and the dashboard guide says a third thing, an AI assistant may follow the wrong instruction.

    Why it matters: Agents treat manifests and context files as routing truth.

    Do this next: Compare README, CONTEXT.md, dashboard docs, and checkyourself.manifest.json for contradictions about where agents should start and which dashboard path is default.

    Success signal: A new agent can answer which file to use without choosing between conflicting instructions.

    Triggered by: CY-P2-002

    Learn from: Diataxis: Start here

  • Make CI prove the same things you prove locally

    CI is the robot checklist that runs when you push changes. It should cover the checks you trust before calling a repo ready.

    Why it matters: Checks used to call a repo ready should be represented in CI or documented as manual gates.

    Do this next: List every command you trust before launch. Put safe repeatable checks in .github/workflows/validate.yml and keep local-only checks in the launch checklist.

    Success signal: A broken JSON file, Python syntax error, or accidental generated file fails before release.

    Triggered by: CY-P2-003

    Learn from: GitHub Docs: Quickstart for GitHub Actions

  • Separate works-here from published-and-proven

    A clean local repo is a good sign. It is not the same as a public repo with passing Actions, readable README, visible images, and release notes.

    Why it matters: Local green status is not the same as GitHub Actions passing after push.

    Do this next: After publishing, open the repo like a visitor. Confirm README rendering, image rendering, Actions, and release notes.

    Success signal: A stranger can use the public GitHub page without private context from this workspace.

    Triggered by: CY-P2-004

    Learn from: GitHub Docs: Managing releases in a repository

  • Test the AI with one known-bad example

    If CheckYourself is supposed to catch risky app patterns, it needs at least one fake risky app to practice on.

    Why it matters: Prompt systems need small known-bad inputs to catch shallow diagnostic behavior.

    Do this next: Give samples/dogfood-fixture-broken-app.md to one AI tool with the CheckYourself prompt. Check whether the answer includes all 20 coverage rows, a complete backlog, approval gates, and a learning plan.

    Success signal: The AI does not stop at top three issues and does not start fixing before approval.

    Triggered by: CY-P3-004

    Learn from: OpenAI Cookbook: Getting started with OpenAI Evals

  • Check visual outputs like a user

    An HTML dashboard can be valid code and still be hard to read. Open it and confirm a normal person can understand it.

    Why it matters: The dashboard is part of the product experience, not just a generated file.

    Do this next: Open the generated dashboard, compare it to the Markdown report, and save a screenshot when it is part of launch proof.

    Success signal: The screenshot shows the score, finding counts, backlog, and learning section without broken layout.

    Triggered by: CY-P3-005

    Learn from: Chrome for Developers: Lighthouse overview
